# MusterOffice 替换收益与桌面包体积评估

2026-09-24 · 基于本地实际安装包拆解与既有性能记录。**旧包体积已测；新内核体积和性能未测，以下预测有明确条件，不是发行承诺。**

## 1. 结论与适用范围

对本次检查的 **macOS arm64、Musterwork 0.2.4 标准验收包**，完整替换 PPT 执行链、保留现有全部受管字体以及其他产品功能后，建议按以下范围规划：

| 指标 | 实际旧基线 | 替换后的规划范围 | 预计减少 |
| --- | ---: | ---: | ---: |
| 标准 DMG 下载 | 735.27 MiB | **300–360 MiB** | **约51%–59%** |
| App 逻辑文件总量 | 1667.31 MiB | **570–650 MiB** | **约61%–66%** |
| 保守的大依赖情形：DMG | 735.27 MiB | 350–420 MiB | 约43%–52% |
| 保守的大依赖情形：App | 1667.31 MiB | 660–730 MiB | 约56%–60% |

规划中心可取 **DMG 330 MiB、App 610 MiB**。这里的“完整”指一期内核与现有中英文字体档案可离线使用，不表示预装全球全部字体、任意模板/视频素材或整个产品其他按需组件。Windows、Intel Mac、universal 和其他产品 offline 变体需要各自重新测量。

体积收益比性能倍数更容易估算，因为实际包里存在可明确归属于 PPT 的重型运行依赖。性能主要看 Office/PDF 转换的消除、持续编辑和内存，而不能从“Rust”推出固定加速倍数。

## 2. 基线身份及测量方法

本次只读挂载实际 `Musterwork-0.2.4-arm64.dmg`，检查内部 `.app`；没有启动它、修改签名、重新打包或发布。包内 metadata 确认 `standard` 变体。

- DMG：770,986,644 bytes；SHA-256：`ba8948f2961b6b2e79f1696a3080963c1e62fc796477a7733394e83a3d65ac83`，与验收说明一致。
- 验收说明记录源码提交：`a059ffc4c7ff16617abe0fb05050fd1f4d11fd44`；该包是本地验收产物，不据此声称已公开发布。
- App：16,784 个普通文件，合计 1,748,304,657 bytes；符号链接不重复跟随，没有发现重复硬链接。
- 安装量使用普通文件逻辑长度，不等于所有文件系统上的分配空间，不含用户缓存/文稿。MiB 为 1024² bytes；735.27 MiB 约为十进制771 MB。
- 逐文件 gzip level 6 得到压缩代理值 775,624,198 bytes，比实际 UDZO DMG 大0.60%。该接近只说明旧包拆账代理有参考价值，不证明新包也有相同误差。

机器证据见[测量与假设清单](evidence/2026-09-24-package-benefit-estimate.json)。该 JSON 同时区分本次测量、历史记录与未测预测。

发现的其他同版本基线不能混用：本机已安装的0.2.4 App只有约404.24 MiB，PPT资源约21.21 MiB，缺少本次大包中的完整原生组件；旧 `latest-mac.yml` 指向约176.51 MiB的DMG，与此次735.27 MiB验收包不同。仅按版本号、源码 `resources/` 或当前安装目录估算会严重失真。

## 3. 实际包构成

| 部分 | App内逻辑MiB | gzip6压缩代理MiB | 替换时的处理 |
| --- | ---: | ---: | --- |
| PPT专用LibreOffice | 724.35 | 274.40 | 由自己的文稿语义、Reader/Writer、渲染替代 |
| PPT专用Chromium | 195.05 | 87.48 | 自有排版/绘制不再需要此独立浏览器 |
| PPT专用Node | 104.91 | 33.53 | 原生宿主替代其PPT执行职责 |
| Poppler及其闭包 | 19.87 | 7.23 | 自有最终PPTX重读/渲染/字体证据替代PDF中间链 |
| 当前受管完整字体 | **115.41** | **94.30** | **本次标准估算全部保留** |
| 旧PPT依赖的sources归档 | 63.44 | 61.39 | 对应依赖退役后重新审查分发义务，不作为“可随便删掉”的文件 |
| JS引擎/Playwright重复副本、清单、许可等 | 51.23 | 10.07 | 新内核及其真实清单/许可取代；不能假定新成本为0 |
| 非PPT应用整体 | **393.06** | **171.30** | **全部保留** |
| 总计 | **1667.31** | **739.69** | 实际DMG为735.27 MiB，代理不是实际安装包 |

PPT链路合计 **1274.25 MiB，占App逻辑量约76.4%**。扣除保留字体后，可被新实现替换的旧闭包约 **1158.84 MiB（1.13 GiB）**。这里删除的是专属于PPT的依赖；Electron框架本体约270.27 MiB以及其他Agent、浏览器、连接器能力没有算成收益。

仅修剪两份重复JS/Playwright、移出某些发行资料也能减少一部分旧包，但不能代表重写内核的全部收益。核心结构性收益来自不再随PPT携带通用Office套件和额外浏览器/Node/PDF工具链。

## 4. 新包估算公式与假设

标准情形保留393.06 MiB非PPT应用和115.41 MiB现有字体。为新完整演示内核、宿主桥接、图形/塑形、动态/3D、必要codec及少量新增数学/模板资源预留 **60–140 MiB安装量**，对应 **20–70 MiB压缩量**；新安装器元数据及模型偏差另留 **5–15 MiB**。

这些新增范围是工程预算假设，**不是已构建的Rust/Skia/codec组合测量**，也不是把原来的“静态原生≤30 MiB”直接当作完整一期内核大小。依赖版本、裁剪配置、媒体策略和新增字体决定实际值。

```text
App = 393.06 + 115.41 + 新闭包(60～140)
    = 568.47～648.47 MiB → 规划约570～650 MiB

DMG代理 = 171.30 + 94.30 + 新闭包压缩(20～70) + 余量(5～15)
        = 290.59～350.59 MiB → 规划约300～360 MiB
```

若新依赖/codec/资源达到150–220 MiB安装量，按压缩70–120 MiB及额外10–25 MiB余量，规划App约660–730 MiB、DMG约350–420 MiB。超出这些假设时直接代入实际值重新计算，不能为守住数字删掉高级功能或字体。

如果选择小初装包，只预置常用CJK无衬线和拉丁字体，其余字体/组件在首次使用前下载，可进一步规划 **220–280 MiB初始DMG**。这是分发策略收益，不能宣称全离线成本也下降到该值；涉及未预置字体的任务必须先取得完整资源，不能悄悄换字或只嵌入已有字形。

保留Electron和当前完整字体的压缩代理就已经约 **265.59 MiB**。因此，在上述条件下“整个Musterwork标准包压到几十MiB”不是合理目标；不能把仅核心库的尺寸宣传成整个桌面产品。

该估算尚未计入未来非PPT产品功能增长，也没有把其他组件改为按需下载冒充PPT减重。动态更新补丁大小与完整DMG不同，应另算。

## 5. 性能收益：已有记录与新目标分开

历史原始数据本轮重新读取，但没有重新跑业务基准。浏览器数据来自2026-09-23的优化后记录；桌面原生数据来自2026-09-13，不能把旧优化前160秒对照当成当前日常基线。

| 维度 | 可核对的现有记录 | MusterOffice设计目标/可预期变化 | 目前能下的结论 |
| --- | --- | --- | --- |
| Web 10页完整导出 | 冷组件缓存7.714s，热缓存6.709s | W-S10资源就绪P95≤5s | 有改善目标；样本/统计/缓存口径不同，尚无已测加速比例 |
| Web 40页完整导出 | 冷8.818s，热8.241s | W-S40同口径P95≤8s | 现有优化后已接近目标，不能承诺10倍加速 |
| 桌面单页修改后完整产物 | 5种负载修改P95约5.53–11.46s | 局部可见反馈P95≤300ms，完整ZIP另算 | 交互潜力大，但不能把完整导出耗时除以300ms声称20–30倍 |
| 原生内存 | 历史负载进程树RSS约1.90–2.26GiB，共享页可能重复计数 | W-S10/S40宿主+核心增量目标256/512MiB | 可减少重型进程和重复表示；需统一CPU/GPU/共享页口径后才报节省百分比 |
| 主线程响应 | 优化后10页最长65/107ms；40页冷102ms | 办公计算移出主线程，目标无>50ms办公计算长任务 | 自有可调度计算更可控，但UI/GPU/系统仍需实测 |
| 运行组件初次加载 | 浏览器现有soffice.wasm/data原始合计约280.98MiB | 静态WASM闭包压缩目标≤15MiB，动态/字体/codec另计 | 原始大小与压缩大小不能相除计算“缩小倍数”；减少通用Office载荷有明确方向 |

浏览器样本为同内容页面扩展的10/40页文稿，能复用字体子集；总时间包含测试结果包检查，不含模型生成和真实云上传，本地HTTP/OS缓存可能已热。它不是全部真实用户文稿，也不是公网冷下载。原生记录使用M4 Max、macOS26.2，每种修改仅5次，P95是描述统计；现有方案本来就有39/39未改页布局复用，因此不能把“新增增量缓存”当作全部新收益。

纯计算时间更准确的模型为：

```text
当前：布局 + OOXML写出 + Office再打开/转换 + PDF/页图/字体证据 + 上传提交
替换：原生布局/场景 + OOXML写出 + 实际PPTX重读/检查 + 自有预览 + 上传提交
```

新路线减少通用Office冷启动、PDF中间表示和跨进程材料交换；但真正的字体塑形、复杂图表/SmartArt/数学、图片解码、媒体播放、文件检查仍有成本。模型生成、找图、网络上传和产品提交不因换内核自动加速。

对端到端任务，应使用 `T_new = T_model + T_assets + T_new_compute + T_upload + T_commit`。举例，模型60s、资源/上传20s、计算8s的任务，计算即使降到4s，总时长也仅从88s降到84s，约4.5%；这只是算术示例，不是用户当前测量。持续编辑与预览更可能让人明显感到变化。

## 6. 质量、维护与资源收益

| 收益 | 机制 | 兑现条件 |
| --- | --- | --- |
| 预览/导出/修改的一致性 | 同一领域模型与编译计划，不在DOM/OOXML/Office/PDF多种解释之间往返 | 同源本身不能认证正确；真实文件及Office/WPS回存仍须通过 |
| 高级功能 | 原生动画、媒体、SmartArt、公式及扩展对象进入模型和操作 | 逐项创建、修改、播放、写出、目标应用编辑，不只保留缓存 |
| 失败定位与恢复 | 对象级诊断、显式预算、取消检查点和宿主fence | 不减少必需检查；每阶段取消/崩溃/晚结果回归 |
| 用户资源占用 | 去掉PPT专用Office/浏览器/Node进程和重复中间产物 | 新图形/解码/GPU闭包同样计量，不能只看Rust heap |
| 维护和自主可控 | Office语义、布局、格式规则在自己负责的模块中修复 | 这是长期能力收益；也意味着自己承担格式兼容与回归维护，并非维护成本归零 |
| 跨产品复用 | MCP/Skill/Plugin/SDK调用同一能力 | 独立客户端验证，不依赖Musterwork私有源码 |
| 分发成本 | 标准DMG每次完整下载少约375–435MiB | 1万次完整下载约少3.6–4.2TiB传输；增量更新/CDN成本按实际策略另计 |

输出PPTX也不保证同等比例变小。当前完整可编辑字体、图片、视频仍需保留；示例浏览器10页PPTX约26.55MiB，40页约26.73MiB，资源本身占主要部分。新Writer可去重/流式压缩，但不能用删字体、降低图片质量或移除视频制造虚假收益。

## 7. 将估算变为可验收收益

E0记录新静态/完整动态/字体/codec闭包及压缩量；E1按相同输入、字体、输出质量、检查阶段、设备、缓存模式重跑旧基准；E3/E4实际重建同架构标准DMG并比较摘要清单，另测冷启动、单页可见反馈、完整导出、100次循环和媒体/GPU资源。

建议体积评审点：标准DMG以330MiB为规划中心；达到360MiB以上需逐项解释新增闭包，420MiB以上需重新评审完整依赖。它们是本次估算的检查线，未经实测不能替代原设计预算或成为强制删功能的理由。

最有把握的判断是：**对本次携带完整原生PPT工具链的包，完整替换具有显著减重空间；标准包减半左右是合理规划。性能和质量提升需要E0及同口径回归，不能现在承诺固定倍数。**
