# ADR 0003：Rust 主体、TS 接入与精选 C/C++ 组件

- 状态：**Accepted（技术方向与选型原则）；具体组件和实验结果未确认**。
- 日期：2026-09-24。
- 依据：用户询问 C/C++ 是否有必要，并要求性能、质量效果和体积做到极致；在获知“Rust 主体＋精选底层组件＋TS 薄封装、按实际结果裁定”的建议后，明确回复“可以，我同意这个方案”。

## 决定

1. Rust 是文档语义、事务、引用、布局/时间规则、格式与诊断的主体实现方向，提供原生与 WASM 目标。
2. TypeScript 负责 SDK、浏览器及 AI 产品接入。核心计算不依赖 Node.js，也不在 TS 中维护第二套布局、格式或动画规则。
3. 不设“所有依赖必须纯 Rust”的限制。字体、绘制、图像/媒体和其他底层计算组件同时评估 Rust 与 C/C++ 实现；选择依据是同功能与同质量下的端到端速度、内存、体积、跨端行为和维护可控性。
4. C 适合作为窄接口及特定基础组件的语言，不作为整个复杂文档内核的默认主体。C++ 保留为有竞争力的组件或主体对照路线。
5. 跨语言接口应粗粒度、类型/所有权明确、有界并可审计；不能逐字形/逐帧对象频繁跨边界，也不能同时维护两份语义事实。WASM 的链接、线性内存及运行时闭包需独立验证，不假设与原生 FFI 相同。
6. 质量、原生编辑性和完整能力是硬门槛；不能用语言纯度或片面包体指标牺牲这些要求。完整依赖、字体、媒体和生成文件体积分别测量。

## 对后续选择的影响

E0 按同一语料比较 Rust 为主、必要的 Rust/C++ 混合及 C++ 主体对照。对照不要求先写三个完整内核；采用能裁定核心风险的最小纵向实现。若证据支持改变主体方向，记录新 ADR 和依据，不隐式更改本决定。

具体图形、字体、codec、XML/ZIP 组件、ABI 细节、编译参数、许可证与发布包名仍待决定。CPU/GPU 后端依然服从完整播放与跨端验收，不能从语言名称推导性能或质量。

## 授权与实施状态

本次确认技术方向并继续完善设计，没有启动源码开发、依赖安装或选型实验。“方案全部实现后的接入方式”是设计问题，不等于已经授权执行全部实现。技术方向不再标为 Pending；具体 E0/实现范围仍按工程规范确认。
