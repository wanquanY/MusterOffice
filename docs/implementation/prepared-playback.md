# 播放帧的准备与完成边界

2026-09-27 · 接续[分步绘图组件](stepped-raster.md)。Rust 播放计划现在可以先生成持有完整校验上下文的待完成帧，由宿主执行组件，再回到原播放实例完成校验。此阶段完成 Rust 边界及真实原生分步组件验证；TS/WASM 播放 owner 的对应接口、浏览器调度和端到端取消仍须继续接入。

## 单一计算与验证路径

`CompiledRaster::complete` 消费原编译批次，检查组件状态、失败时不得携带像素、完整长度、预乘颜色通道，并计算像素与原始绘图指令的摘要。原同步渲染也调用此方法。`CompiledScene`、图片场景、自建文稿和导入 PPTX 的待完成帧复用这条路径；没有通过拦截回调、抛出异常、再次执行文稿编译来模拟暂停调用栈。

`PlaybackSession::prepare_render` 和 `PptxPlaybackSession::prepare_render` 返回不可从 JSON 构造、不可克隆的 Rust 对象。对象暴露只读绘图指令，以及来源帧的只读图片资源；宿主可以将它们交给上一阶段的组件 `begin/step/take/drop`。宿主在步骤之间调度其他工作或取消，最终以 `complete_render` 消费同一个待完成帧。

待完成帧持有私有实例身份、计划摘要、求值后的时间和完整播放绑定。完成时重新检查实例、计划与 generation；即使两个播放实例收到完全相同的公开 session 字符串与文稿，也不能交换待完成帧。旧 generation 或已 dispose 的实例不再交付该帧。这里只管理文稿计算生命周期，不增加任务数据库、权限系统、界面、隐式时钟或全局句柄表。

组件输出属于可信计算端口。宿主仍必须把对应调用的返回值交还对应帧；长度、通道和摘要校验不是对任意像素的渲染真实性证明，也不代替 Worker/进程响应关联。`PlaybackCompletionFailure` 分开返回原诊断与组件隔离处理标记；接入方必须执行要求的失效处理。丢弃未执行的帧、正常关闭组件任务和复用已经失效的组件是不同操作。

## 资源生命周期

来源计划一次解码、验证图片；待完成帧与计划通过 `Arc<PreparedImages>` 共享不可变资源。不会为了解除 Rust 借用而按帧复制或重新散列整个图片包。计划先释放时，待完成帧仍可安全读取资源，但已 dispose 的播放实例拒绝其完成；最后一个所有者释放后，资源对象随之释放。它不代表操作系统 RSS 立即下降。

Rust 所有权保证每个帧最多完成一次；提前 drop 释放其几何和资源引用。宿主负责限制同时持有的帧数与总内存，核心没有后台队列或跨调用缓存全部帧。编译后的批次只属于当前实现和组件 profile，不是跨版本持久化 checkpoint。

## 验证与限制

原生验证使用既有 SDK 的 10 个 owner、71 个冻结帧；Rust 准备后，将指令与图片送入真实 C++ 分步探针，以 1、7、4096 三种工作批量执行，共 213 次完整像素和全部帧元数据比较。来源/字体输入在首帧前释放，图片解码与文本塑形使用真实原生组件。探针是验证宿主，产品原生 worker 尚未增加这一分步协议。

生命周期检查覆盖不同实例、generation 变化、dispose、准备后放弃、完成时取消、无效返回及不可复用组件状态；共享资源检查直接验证保留原分配地址和最后一个引用的释放。实际命令、失败修复与最终源码绑定见[阶段证据](../reviews/evidence/2026-09-27-prepared-playback-verification.json)。

受影响的 raster、render、presentation-compile、kernel-api 四库共 235 项测试通过；15 步仓库门禁包含严格 Clippy、119 份不变 Schema、TS 检查和既有原生播放/导出/CLI 集成。忽略项和筛选项以日志逐项记录，不计入已执行用例。重新构建 Rust WASM 后，现有同步 SDK 在独立 Node Worker 中重验 71 帧，完整像素与元数据也与原生 SDK 参考一致。这证明共有计算路径的回归结果，不代表新待完成帧已暴露给 JS，也不代表浏览器分步播放已经验收。此次本地回归包未发布，没有给出性能提升或产品安装包体积结论。

此阶段没有改变格式语义、动画范围或数值容差，也没有接入 Musterwork。准备阶段、单个 Skia 绘制操作及完成阶段仍存在同步工作；工作单元不承诺耗时上限。接下来继续打通 TS/WASM 的持有与释放、宿主让出/取消、组件错误隔离，随后推进更细粒度的计算中断和完整替换验收。
