# 播放帧的分步像素校验

2026-09-27 · 承接[扫描分派](scan-dispatch.md)和[TS/WASM 分步播放](wasm-stepped-playback.md)。阶段证据见[校验、实际播放测量与产物](../reviews/evidence/2026-09-27-pixel-validation-verification.json)。本阶段保持完整一期目标；没有修改 Musterwork、启用产品替换或新增 UI、权限、存储。

## 问题与实现

实际 SDK 的初步测量发现：除绘制外，完成阶段也会同步扫描整个像素缓冲区，检查预乘 Alpha 并计算 SHA-256。仅将 Skia 绘制拆分，不能解决这段随分辨率增长的连续计算。逐步发送 Worker 消息还会叠加传输开销；诊断同时比较远端逐步、Worker 内连续驱动、Worker 内定期让出三种方式。

`mo-raster::RasterReplyValidation` 显式持有完整返回的像素、摘要状态和游标，每个工作单元校验并哈希不超过 16 KiB。状态/大小不合法、非法预乘像素与取消均不能产生部分成功结果；失败终结该游标，丢弃游标释放其所有权。工作单元范围仍是 1–4096，不代表固定耗时。

完成后只能取得字段私有、不可自行构造或修改的 `ValidatedRasterReply`。共享完成函数接受这个证明或原始回复；原始回复执行同一套校验，证明路径不再重复扫描像素。尺寸匹配、绘图指令摘要、实际 owner 身份、计划、generation 和 dispose 检查仍执行。该证明只覆盖像素格式与摘要，不代表已经验证几何绘制正确；画质仍需要独立参考。

WASM 待完成帧的 `begin_validation` 在返回前把有界组件结果复制到 Rust 自有缓冲区。外部 JS 数组随后修改、释放不会改变已进入校验的数据。该阶段不新增一份全帧拷贝，也不引入跨让出点的外部可变内存借用。失败标记始终可读，宿主适配器不能以取消掩盖已观察到的组件故障。

TS `PlaybackExecution.step` 先驱动组件；绘制完成后接收、快照结果并释放组件任务，再推进 Rust 校验。直到校验完成才返回 `complete=true`；`take` 消费证明和待完成帧，执行最终绑定检查并交付像素。正常 close 在绘制、快照后、校验中或校验完成后均释放独占租借；健康 owner 可继续采样。校验发现组件错误时立即报告并隔离，无需等调用方 take。

全部时钟、Worker 消息、让出和发布仍由宿主掌握。没有向核心添加计时器、异步任务平台或后台调度器；[计时程序](../../tools/verification/playback-costs.mjs)及其 [Worker 包装](../../tools/verification/playback-cost-worker.mjs)仅是对真实开发包的诊断工具。

## 验证与局限

共享 Rust 检查覆盖 16 KiB 前后边界、空/尾部长度、各颜色通道错误、每个取消检查点、提前取结果、尺寸不匹配，以及校验后 owner/generation/dispose 变化。TS 测试覆盖两阶段所有权、回调重入、异常清理与故障即时隔离；原同步完成入口继续回归。

真实 Node/Chrome 播放与原生参考的完整像素及元数据独立比较。WASM 生命周期验证分别运行原同步完成入口和新校验入口；后者新增外部缓冲区修改、提前完成、尾部坏像素、校验中取消再采样，以及通过真实 TS 接口立即报告校验故障。它们是所有权和错误路径检查，不是新增 Office 文稿画质语料。

最终 **21 步门禁通过**：全工作区 Rust **946 项成功、24 项默认忽略**，另运行真实 worker 的绘制/播放/导出/CLI 专项；不能把这理解为全部忽略项都已补齐。119 份 Schema、严格 Clippy、TS 与 Native/WASM 文稿一致性通过。受影响四库的 239 项专项与全仓测试重叠，TS 21 项也与门禁重叠，不累计成新增覆盖。首次新增测试因整数类型未明确而编译失败，修正后专项和全仓通过，失败记录保留。

Node/Chrome 各 **71 帧**的全部像素和元数据一致；Chrome 153.0.8010.53 隔离环境另通过 30 次既有步骤间取消。原同步完成接口 **26 个**、新校验接口 **36 个**独立真实 WASM Worker 用例通过，其中新接口含两种 owner 的六次校验阶段取消再采样。两份放大文稿另外经当前原生 worker 重验，并与后续计时使用的全部参考字节及元数据一致。

本阶段仍保留同步临界区：文稿/帧准备、部分绘图 primitive、结果分配及快照、指令摘要、元数据序列化、最终输出复制与析构。像素校验变为可让出不等于整条链路的严格时限；大工作预算仍可连续处理大量字节。完整吞吐、取消响应、实际计算停止和物理 RSS 必须分别验收。

## 测量与体积

最终实测统计与构建门禁在本阶段证据中登记。测量使用两份自有 4:3 文稿放大至 **1440×1080**，保留原比例，不是 1920×1080，也不是完整 W-D 或媒体工作负载。来源样例使用固定自有合成字体，禁止隐式网络和系统字体。固定原生 SDK 输出作为像素与元数据参考，全部比较在计时区间之外进行。

每版本/输入独立准备一个 Worker，首次采样另记；之后每种模式采样 30 帧，六种“版本×模式”顺序轮换并反转。报告 P50、P95、最大值及失败结果，保留所有实际观察。WASM 和组件内存已热，操作系统缓存、GC 与整机其他负载没有强制控制；Worker 内让出的时间包含在端到端耗时中，不能称为 CPU 时间。主机为 Apple M4 Max、36 GiB、macOS 26.2，具体 Node/V8 与组件摘要绑定在报告中。

计时运行于 Node **23.5.0** / V8 **12.9.202.28-node.12**。A 组先创建旧版 Worker，B 组反转创建顺序；每组各 360 个计时帧，另四个首次采样，均完成全像素与元数据校验。一次与证据哈希检查短暂重叠的中间批次保留在本地记录中，不纳入下面两组比较。

以下只展示 **Worker 内连续驱动**，单位 ms；该模式便于区分计算成本，本身不提供消息取消响应。其余逐步 RPC、定期让出模式及所有最大值都在证据中。

| 来源 A | 33.258 / 35.638 | 35.056 / 38.537 | 13.752 → 0.531 |
| 作者 B | 14.085 / 15.003 | 14.207 / 15.102 | 13.080 → 1.852 |
| 来源 B | 34.880 / 37.567 | 35.509 / 39.545 | 13.457 → 0.559 |

常见的整帧同步校验调用已拆开，但整帧中位数仍略有增加；不能宣称吞吐改善或无回退。两组来源样例中，完全相同的 Skia 组件 step 总耗时中位数也随 Worker 变化（旧/新分别为 20.201/22.121 ms、21.954/22.426 ms），未将这部分差异直接归因为本次算法改动。B 组来源新版还出现整帧 **58.861 ms**、单次校验 step **17.050 ms** 的最大值；仅有墙钟观察，原因未确定，不能擅自归因为 GC 或系统抢占，更不能将 P95 改善当成最坏时限证明。

逐步 RPC 的消息数从作者 52 次变为 107 次、来源 481 次变为 536 次，因为新增校验步骤也跨线程请求。Worker 内推进仍只需要一次请求，定期让出模式由诊断宿主以约 2 ms 的时间片请求 `setImmediate`；实际返回间隔受同步工作和调度影响。正式核心不持有这个时间片，也未因消除消息往返而取消让出需求。

两次独立打包产物逐字节相同：**60 文件、清单外 14,424,509 字节、归档 4,149,704 字节**。相比前阶段，清单外增加 **15,079 字节**、归档增加 **3,470 字节**；其中 Rust WASM 增加 **8,124 字节**，Skia/HarfBuzz 产物不变。

离线开发包仍为 `releaseCleared=false`；体积只统计这个已实现的播放包，不推算完整办公内核或 Musterwork 安装包。Rust/TS 接口与它们的匹配 WASM 同包更新，没有改变 JSON Schema、图形组件、依赖版本或许可证。
