# Musterwork 内容文件持久回收

2026-09-26：延续[物理写入恢复](product-content-lifecycle.md)，补齐引用撤销后、实际删除前中断的恢复责任。以下 `MW:` 路径属于产品仓库；本仓库保存相对路径、摘要和验证材料，未迁入产品私有源码或数据库。本阶段保持原有 Rust 内核、Native/WASM、SDK 和 worker。

## 事务中的回收责任

`MW:apps/agent-runtime/crates/infrastructure/sqlite/src/schema_v184.rs` 在既有 SQLite owner 中增加 `content_material_retirements`。以 tenant/hash 唯一登记待核对的物理内容，递增序号用于分批处理。内容墓碑、内容行删除或换绑、准入 stage 删除或换绑、物理写入登记释放或换绑，均通过数据库触发器在原事务中登记旧 hash；事务回滚同时撤销登记。

迁移从 v183 到 v184，回填历史墓碑引用的不同 tenant/hash。它不遍历未知 CAS 文件，不把已发布但没有业务使用者的内容自动判为可删除。READY 元数据、准入 stage 和物理写入登记仍是物理引用；业务生命周期继续由原 Runtime 决定。新的准入 tenant/hash 索引支持回收查询，避免每个文件遍历租户的准入历史。

## 唯一删除路径

`MW:apps/agent-runtime/crates/infrastructure/sqlite/src/content/material/retirement.rs` 统一承担 CAS 删除。物理写入恢复先清理临时文件、释放写入登记并提交；释放登记会生成回收责任，随后进入同一 CAS 回收流程。

一次普通回收最多检查最早的 64 个不同 hash。在现有注册锁和 writer fence 保护下，重新查询三类引用；仍有引用则保留文件并清除本次登记。该引用未来释放时会重新登记，因此受保护项不会长期占据批次前部。无引用时，先删除文件并同步目录，再删除回收登记、提交事务。文件错误向上传递，尚未完成的责任保留。

直接删除还会按唯一索引核对该次请求的目标，避免大积压使本次删除过早返回成功。Future 取消不会解除已排队文件操作所持有的注册锁。重试发现文件不存在时仍同步最近存在的父目录，覆盖此前 unlink 成功而目录同步未完成的窗口；之后才能清除持久登记。

`reclaim_storage_if_idle()` 已接入内容回收，与数据库 vacuum 阈值分别判断。现有产品维护流程调用这个入口，不新增后台定时器或任务队列。启动、后续写入、直接删除及显式恢复也会执行回收。单批之后如有积压，通过 `retirements_pending` 表达；不把一批成功解释为全部历史文件已清空。

## 验证

最终 SQLite 内容、准入、共享内容、迁移与启动维护筛选 48 项通过，生产库严格 Clippy 和所改 Rust 文件格式检查通过。初次构建发现测试暂停钩子的模块可见性错误，修正后第一轮 48 项通过；增加准入索引与查询计划断言后，在最终源码上再次运行全部 48 项并通过。没有执行整个产品的全部测试。

新父测试真实终止四个子进程，分别停在墓碑事务已提交、文件已删除、回收登记已删除但事务未提交、删除完成四个边界。终止后独立读取旧 SQLite 状态，再启动产品存储：前三个边界仍有持久登记，最后一个没有；恢复后均保留墓碑、清空登记并确认文件不存在。先前四类写入退出场景也在最终源码上重新通过。

取消测试让真实 unlink 排在唯一阻塞工作线程之后，确认已入队才取消 Future；排队期间注册锁继续持有，操作完成后文件消失而事务登记仍在，下一次恢复完成目录同步并清除登记。其他测试覆盖删除失败后重试、准入释放与回滚、引用保护后再次登记、64 项批次、公平推进和积压后的目标删除。实际 SQLite 查询计划使用新增的准入覆盖索引。

[旧库验证驱动](../../tools/verification/product-content-retirement-migration.py)在产品忽略目录中运行上一阶段冻结的真实 v183 测试程序，生成两份旧库后实际终止进程。新程序将两份库升级至 v184：已发布内容保持原字节；旧墓碑对应文件被回收。墓碑用例在旧库中释放写入登记，确保结果来自迁移回填，而非写入恢复顺带生成的回收项。另有迁移晚期失败回滚测试，以及保留旧数据的 v182 升级回归。三项 ignored 入口是由父测试或驱动显式调用的专用入口；本阶段共执行十次真实进程终止、两次外部旧版本升级。

通过当前产品内容存储写入、回读的两页交付包含 12 个资产和 bundle，共 13 个文件，与上一阶段封存字节一致；固定摘要共享内核 CLI 重新检查后报告也一致。测试输出的 `files.json` 是索引，不计入这 13 个内容文件。[阶段证据](../reviews/evidence/2026-09-26-product-content-retirement-verification.json)绑定最终源码、原始日志、旧程序身份、迁移观察和实际产物。

## 继续推进的边界

物理引用回收不等于 Artifact/Invocation 业务保留策略，也不提供完整作业总额或全盘容量上限。此前 512 MiB/1024 项仍只约束在途物理写入。旧命名空间外暂存、未知历史 CAS、已发布但无业务引用的内容、云端存储仍须各自实现和验证。

实际强制退出验证不证明硬件断电、内核崩溃或 Windows 文件系统行为。没有由本阶段新增内核性能、RSS、吞吐、安装包体积或 Office/WPS 兼容结论。

后续继续串联产品作业预算、不可变范围读取、原生生产者和最终候选验证，以及原 Runtime 下的 Artifact/Ledger/成功回执原子提交。Viewer/Player、历史兼容、完整高级内容及 E0–E3 替换门槛继续开放。
