# 显式 OPC 类型声明修复

2026-09-30。两个真实平台模板各有 13 条指向不存在母版部件的 Override 声明。
普通导入继续要求完整包结构；本轮增加独立的、来源摘要绑定的修复计算，
而不是在渲染时删除声明、忽略错误或构造缺失页面。

依据 [ECMA-376 Part 2 第五版](https://ecma-international.org/publications-and-standards/standards/ecma-376/)
7.2.3.2.1 与 7.2.3.2.5，Default 是扩展名映射，Override 是具名部件映射。
实现仍保留严格 OPC 入口；异常来源必须显式选择修复，并保留原始文件。

## 计算与接入

`mo_opc::ContentTypeRepair::inspect` 复用普通读取的 ZIP、CRC、XML、容量、部件和
关系检查，只允许收集无实际部件的类型声明。丢失关系目标、损坏压缩包、重复部件、
非法 XML 等继续失败。签名包需要另行签名政策，不能通过此入口修改。

检查返回原始包 SHA-256 及完整待删除声明列表。`write_sealed` 要求调用者提供
已核对的来源摘要和私有结果 sink。核心只修改 `[Content_Types].xml` 中已识别的元素；
XML 编码、注释、前缀和其余字节保留，所有实际部件继续复制原压缩字节。
新结果封存后重新使用普通严格读取，并核对部件、关系与类型映射；写入回执
不是产品发布、视觉验收或模板入库的替代品。无修复项时返回逐字节一致的包。

通用 XML 元素删除使用原始元素序号和展开名，拒绝缺失、重复、重叠或根元素选择，
复用有界扫描、取消检查和保留 UTF-8/UTF-16 编码的字节编辑器。

Rust SDK 可通过 `sdk::opc` 使用相同计算。CLI 是本地文件薄适配：

```sh
mo-cli opc-repair-inspect source.pptx
mo-cli opc-repair-apply source.pptx <检查返回的来源SHA-256> repaired.pptx
```

第二条命令生成新文件和 JSON 修复回执；拒绝覆盖任何现有目标。宿主负责保存
原始与派生来源、修复回执及新版本关系。普通 PPTX 导入、MCP 计算调用和模板队列
不会自动修复输入，也不会暗中改写已冻结的来源摘要。

## 验证范围

60 项 XML/OPC 测试和 1 项实际 CLI 发布测试通过，严格 Clippy 与格式检查通过。
覆盖 UTF-8、UTF-16 双字节序的实际 XML 编辑、原始部件保留、严格重读、幂等、
错误摘要、签名、关系缺失、重复条目、CRC、容量、取消及拒绝覆盖和临时文件清理。

两个真实平台模板的派生文件均通过严格重读：每份保留 79 个实际部件，全部部件
的未压缩及原压缩字节均与来源一致，仅删除 13 条失效 Override。每包原有 19 个
空 ZIP 目录条目未重写；它们不是 OPC 部件。原始文件完全保留。
两份文件继续渲染时均到达实际页面计算，并明确返回尚未实现的段落悬挂标点诊断；
未将导入成功标成渲染通过，也未更改段落属性掩盖缺口。结构修复不证明视觉、
Office/WPS 编辑往返或模板 v3 发布。详见[本轮证据](../reviews/evidence/2026-09-30-opc-content-type-repair.json)。
