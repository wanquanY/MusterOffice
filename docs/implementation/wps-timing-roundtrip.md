# WPS 回存校准与缩放编辑值

2026-09-27。在[原生演示效果组织](native-timing-envelope.md)之后继续双向互操作。完整一期目标保持不变；本阶段不是完整动画、Office/WPS 或 Musterwork 替换验收。

## 实际回存暴露的问题

把上一阶段生产 CLI 直接导出的六对象混合动画复制到自有校准目录，在 WPS 12.1.22553 / macOS 26.2 arm64 中选择红色矩形、向右移动并保存。原生坐标 x 从 1,250,000 变为 1,321,755，证明实际发生了对象编辑。关闭文稿并重新打开，最终仍观察到红/绿/紫放大、蓝色旋转、橙/青还原。最终姿态不证明中间时序一致。

WPS 同时重写了时序：

- 重新编号时间节点；省略部分 dur、restart、repeatCount 和行为默认属性。
- 第一层并行组开始条件变成 indefinite 与父主序列 onBegin 的条件列表。
- seq 加入页面 onPrev/onNext；删去 prevAc=none。
- 删除缩放行为的 attrNameLst。
- 紫色行为的 onEnd 条件保留 1000 ms 延迟，但删除了原来指向绿色行为的 tn 引用。

当前来源计算明确返回 `MAPPING_NOT_IMPLEMENTED: native timing: unmapped content in seq`，原始 OPC 不被改写。不能通过删除导航、猜测缺失引用或统一补回原 Writer 默认值来接受此文件。微软记载 PowerPoint 对缺省 dur 使用 0、对缺省 restart 使用 always，因此“缺省等同无限时长/从不重启”并不成立；WPS 的实际解释仍须独立校准。[Microsoft cTn 实现说明](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/02b2312e-9700-42e0-8a19-b2af1ba83a20)

## 本阶段的导出修正

实际编辑面板还暴露了更直接的问题：显式 from=100%、to=200% 可以播放，但 WPS 的“尺寸”显示为 0%。仅换成 by=200% 的独立对照显示正确的 200%；移动对象、保存并重新打开后仍显示 200%，保存 XML 也保留六个 by 值。重新打开后的放映中，六个矩形均达到约 373–374×279–280 像素的 2 倍尺寸；色区边界允许 1 像素 JPEG/抗锯齿误差。

Writer 现在在两个起始轴都精确等于 100000 时写 by-only；其他起点仍写 from/to。不会舍入 99.999% 或把不同轴的起点视作原尺寸。该选择用于共享行为写入路径，既覆盖平面图也覆盖显式树，不改动时间、重复、fill、对象和节点引用。

by-only 的隐式起点是 (1,1)；显式 to 存在时 Office 忽略 by。因此没有同时补写一个仅供编辑器显示、计算时又被忽略的 by。数值声明只有一个有效来源，维持计算与编辑一致。[Microsoft animScale 实现说明](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/358c6de3-2cd7-459b-8eb9-b90f3721fd12)

这一修正只解决原尺寸起点的缩放参数表达。尚未证明动画属性任意改值、非原尺寸起点的预设编辑、连续多次回存或 PowerPoint 行为；旋转参数编辑也不能由缩放结果推定。真实 WPS 回存文件的来源播放仍受上述主序列语义缺口阻挡。

## 验证与体积

18 步门禁通过，包括 974 项全仓 Rust 测试、119 份合同检查、严格 Clippy、显式原生集成、WASM 构建与公开入口对照。常规测试中的 25 项默认忽略另列；显式集成不代表每个被忽略的环境测试均已通过。23 项时序专项覆盖精确起点判定、非等比/零/最大缩放、重复、往返、fill 与倒退采样；与全仓测试存在重叠。

生产 CLI 导出三份六对象样本，Native/WASM 导出字节一致，18 个 PML/DML 部件通过固定 ECMA XSD。原有两份输入仅把恒等起点的 from/to 换成 by，其他包部件、时序条件和行为参数不变；文件分别从 6064/6161 字节变为 6055/6155 字节。实际在 WPS 校准的 by-only 对照与新生产导出的全部 13 个解压部件逐字节一致，区别只在 ZIP 封装。

36 组作者/来源对照的全部像素、属性值和节点状态相同；72 个新帧与 187 个冻结旧帧，在独立 Native SDK consumer、打包的 Node WASM 分步播放和 Chrome 153 隔离 Worker 上分别通过 259 帧、29 个 owner。五份来源查询在 Native/WASM 上结果一致：三份新导出成功，两份真实 WPS 回存均明确返回未映射。这是跨端一致性证据，不把共享内核结果当作独立 Office 参考。

开发播放包仍为 60 个文件；不含 manifest 的未压缩体积 14,521,878 字节，压缩归档 4,174,400 字节。只有 Rust WASM 变化，原始体积增加 202 字节、归档减少 38 字节；TS、合同、Skia、HarfBuzz 和依赖清单不变。没有新增吞吐、RSS、取消尾延迟或桌面安装包测量，也未重新生成 Rust SDK 源码归档；独立 consumer 验证的是既有稳定协议配合新 worker。

结构检查首轮失败是校验脚本误把文件大小字段作为函数调用；保留原日志与脚本，新版本修正读取方式后全部结构断言通过。一次截图取得编辑窗口而非放映画面，已排除；另一次同时获取放映状态与画面的结果才纳入测量。校准结束后关闭自有标签并恢复原应用，没有修改已有用户文稿。完整摘要与校验材料见[阶段证据](../reviews/evidence/2026-09-27-wps-timing-roundtrip-verification.json)。

## 后续实现约束

后续需要把原生演示效果、点击组和主序列作为有身份的语义对象投影到共享时间求值：

1. 对缺省值、条件列表、indefinite、父节点事件与无显式目标事件分别建立有来源依据的规则。语法接受不代表语义可计算。
2. 导航输入进入内核事件轨迹；实现 next/prev、seek、restart 与重复激活。宿主继续只提供时刻和输入，不替核心补逻辑。
3. 明确编辑效果与子行为的时钟及引用关系，验证原生应用重新编号后依赖仍存在。无法保持的依赖必须有明确诊断，不能被替换成固定延迟。
4. 分别验证初次播放、编辑参数、对象编辑回存、关闭重开、再次回存、来源回读以及点击/导航轨迹。任何一项通过都不替代其他项。

这是既定完整时间图/播放设计的实施约束，不新增产品页面、权限或存储。没有修改 Musterwork；尚不具备开始完整 PPT 替换验收的条件。
