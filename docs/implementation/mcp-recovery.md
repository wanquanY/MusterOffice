# MCP 错误恢复与原生连接生命周期

本阶段继续完善原生 stdio 适配器，保持完整一期目标。[阶段证据](../reviews/evidence/2026-09-26-mcp-recovery-verification.json)关联源码、最终 release、真实协议消息、失败对照和下载文件；之前的 stdio 与缓存元数据证据不覆盖。当前依然不是完整 MCP、跨平台发行或 Musterwork 替换验收。

## 修复及边界

输入先按有界字节行分帧，再进行 UTF-8、严格 JSON、信封及 SDK 方法参数校验。非法 UTF-8/JSON 返回 `-32700`，非法/歧义信封返回 `-32600`，已知方法的非法参数返回 `-32602`。可确定的有效 ID 原样返回，无法确定时省略；有效通知信封不获响应。未知、未声明的方法进入 SDK 的 method-not-found 路径，避免错误地继承默认成功行为。这些错误不会进入业务宿主或占用其任务名额。

输入仍限 4 MiB、输出仍限 16 MiB（均不含换行）；普通请求八个、通知八个。协议错误额外保留一个槽，完整写出前不读取下一帧，复用同一个有十秒期限的输出锁。待发送错误由传输对象持有，所以 SDK 中断并重新调用 receive 时能够接续同一段输出，不会丢弃已写一半的帧。分帧器不重新扫描已检查的前缀。超限/未结束帧、非预期客户端响应、冲突活动 ID 和预算耗尽仍结束连接。

真实进程实验发现，仅关闭客户端输出读取端、保持输入写端开启时，上一版本在 12 秒内不能退出，关闭输入后才结束。原因是原 `tokio::io::stdin` 的阻塞读取不能通过丢弃等待来终止，运行时清理仍等待它。Unix 服务现在使用 Tokio 的[已校验管道构造接口](https://docs.rs/tokio/1.53.1/tokio/net/unix/pipe/struct.Receiver.html#method.from_owned_fd)接入非阻塞事件循环；没有通过跳过清理或放弃宿主线程来结束进程。计算桥接仍正常等待实际阻塞调用结束，再关闭原生调度器。

Unix MCP 服务要求输入输出都是管道；二进制资源子命令仍支持普通文件重定向。非 Unix 开发实现保留原标准 I/O，因此 Windows 的可取消 I/O 与本机验证仍是明确缺口，不能把 macOS 结果推广到全部平台。

## 取消规则纠正

真实 SDK 检查还纠正了先前对新版取消语义的错误解释：[2026-07-28 stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)明确规定客户端通过 `notifications/cancelled` 取消自己的在途请求。服务端向客户端取消订阅的规则，以及 HTTP 按请求关闭响应流的规则，不应套到这里。

之前 SDK 已取消新版请求等待，而适配器只有旧版取消会回收名额，连续新版取消最终耗尽在途预算。旧单元测试只验证了错误的本地假设，没有验证真实 SDK。现在两代 stdio 共用同一请求生命周期：handler 存活时保留名额，取消后 handler 返回才移入有限 ID 历史；已交给输出的响应仍持有其写入预算。真实业务取消仍必须调用 `mo_jobs_cancel`，取消协议等待不会隐式取消文档操作。

失败记录保持可查：首次协议恢复脚本错误地要求新版 ping 成功，已按[新版移除 ping 的规定](https://modelcontextprotocol.io/specification/2026-07-28/changelog)修正检查，并以资源列表检查恢复。首次取消脚本预期新版普通请求不受取消影响，真实结果及官方规范否定了这个假设；修正后的重复测试在旧二进制上又实际复现名额耗尽。没有修改协议来满足错误断言。

## 实际验证

最终构建的 18 项适配器测试、严格 Clippy 和格式检查通过。字节边界、碎片输入、错误帧部分写出、取消竞争及原生阻塞调用的生命周期均有检查。

独立真实进程客户端在两代协议各运行九类恢复错误，并在握手前分别验证一次解析错误恢复；通知不产生响应、四类未知/未声明接口被拒绝、不可恢复输入三类被拒绝。恢复后实际创建两份文档，直接检查数据库确认错误请求没有生成任务。二进制通道权限与非法配置检查保持通过。

两代协议各执行关闭输出和停止读取两种失败：客户端始终保持输入开启，并请求完整工具目录以触发实际输出。全部进程均自行非零退出，慢读取场景触发十秒输出期限。报告保存逐次墙钟时间；这四次故障观测不是产品性能分位数或普遍退出时间上限。等待实际宿主调用退出仍可能耗时，不能用空闲宿主实验声称任意长任务都能立即退出。

两代各执行 11 次真实协议取消。SQLite 写锁使已取得计算许可的调用停留在原生连接/操作入口；另一调用返回限额错误，证明许可实际被占用。取消后额外调用依然不能挤占该许可，解析错误和资源列表却能继续响应。释放写锁后原操作落库；协议不再返回被取消请求的响应，业务 `cancelRequested=false`。连续取消、原业务 ID 重试和进程重连后，仍只有同一个任务、一份文档和一个版本，回执不变。

最终完整业务回归重新完成两代 172 次请求、两次真实导出及 24 份公开资源回读（请求数含随执行时间变化的任务轮询）。实际 PPTX 的 20 个相关 XSD 部件、每份 15 个对象/八段文字及四页 PNG 探针通过，与上一缓存元数据阶段的文件字节/像素检查一致。没有重新声称全仓、完整 Native/WASM、Office/WPS 或产品性能验收；计算工作区与合同源码未变化。

## 依赖及待完成项

Tokio 仍为 1.53.1；仅在 Unix 适配器打开 `net` feature 以获得系统就绪通知，没有创建网络监听。锁文件新增 Mio 1.2.2、socket2 0.6.5，以及目标条件依赖 WASI 0.11.1、windows-sys 0.61.2。五个组件的完整版本、声明许可、源归档摘要和上游许可原文见[组件记录](../../components/io-runtime/component.json)；WASI/Windows 锁定项不等于这些目标的编译或运行证据，完整传递分发审核尚未完成。

最终本机 release 适配器为 12,545,808 字节，含关联宿主和文档计算代码，不含外置绘制 worker、字体、媒体或产品包装；仍不能据此估算完整 Musterwork 安装包。完整 HTTP/任务扩展、独立生态客户端、SDK/Skill/Plugin、跨平台退出、浏览器 owner、全部高级内容与 Musterwork 历史/附件/替换验收继续推进。
