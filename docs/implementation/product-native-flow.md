# 上传至原生定义和压力检查的连续产品链路

2026-09-28，产品实现继续位于独立 `codex/musteroffice-integration` worktree。Musterwork 原主工作区不参与写入、构建或测试。此阶段将此前分别验证的后端与 Runtime 连接为真实跨进程执行，完整替换目标仍在进行。

## 已连通范围

测试从原 Python `TemplateImporter` 上传自有两页 PPTX 开始，沿原策略选择、队列、协调器和签名冻结逻辑，经正式 gRPC 内容与维护接口，进入原 PostgreSQL 准入和环境匹配派发。原模型循环与 Tool 日志驱动固定 SDK/worker，原结果查询接口返回实际完成记录，后端读取实际输出并提交检查点。

两个用例分别运行至 `native_define` 和 `native_stress`。后者在同一次上传中完成定义和全部 8 个固定压力案例；故意提前提交不完整材料、请求越界案例均被原验证逻辑拒绝。已生成的实际结果经内容库传递回产品对象存储，再由原后端检查任务、阶段、请求、来源、字体和设置身份。完成定义或压力计算不能自动发布未完成复核的模板版本。

后端演示文稿表运行原 9 个 SQL 迁移，Runtime 运行原 207 个迁移，位于同一个专用 PostgreSQL 测试实例的不同 schema。原不可变记录、事务、租约、派发与结果查询参与本次链路，不注入伪造的任务完成凭据。后台账户目录的创建不在本用例内：测试仅预置自有用户与账户，并通过明确的账户解析端口读取。

模型路由和模型的工具选择使用确定性测试输入；对象存储使用自有内存实现，所有文稿计算由实际 SDK 执行。测试直接组合生产服务、派发和循环端口，没有启动完整部署拓扑，也没有调用外部模型。因而本结果证明上述连续执行与数据边界，不是外部模型的设计能力或视觉审美验收。

## 联调修正

Python 原执行签名配置允许 `control.grant-key.1`、连续点和空段等标识，而 Rust `DottedKey` 拒绝它们。签名前的通用 Python 校验现在遵循同一语法：总长不超过 160 个 ASCII 字节，每段以小写字母开头，其余允许小写字母、数字、连字符和下划线。新增签名、验证配置及长度边界测试；测试密钥标识更新为 `.v1`。没有修改部署密钥或放宽 Rust 校验。

原自动上传的策略 /3 缺少独立复核模型身份，但后端审查授权必须与冻结策略匹配。新上传现在在存储来源之前解析并冻结模板模型、独立复核模型、各自摘要及 `presentation.visual-review@1` 策略。新阶段准入在传输材料之前核对这些身份，拒绝运行期间的配置漂移。

早期策略 /3 的三个复核字段全部缺失时仍可读取；部分缺失和未知复核策略均被拒绝。已有冻结准入先复用原记录，查询和取消不重新选模型。对没有复核配置的旧任务，新建 `native_verify` 准入明确返回 `template_native_review_policy_missing`；应重新导入生成完整策略，不能改写旧任务、签名或检查点。旧策略 /1、/2 的编码和选择保持原约束。

签名回归还发现旧 BYOK Goal 测试仍期待废弃的特殊 Judge 编码。根据已有 `standing_goal_authority` 的普通 Agent 语义，同步其测试断言，精确核对保留的工具、允许能力、辅助路由与重新绑定的凭据。没有修改 Goal 生产行为。
