# Musterwork 日志内容引用索引

2026-09-27：接续[原生宿主与暂存维护](product-execution-spool.md)，为 Invocation 终态回收补齐原事件日志中的持久引用。协议、SQLite 迁移、原事务提交及真实输出回归已通过；本页不表示已经启用业务内容回收或替换旧 PPT。`MW:` 表示 Musterwork 仓库内路径，私有源码仍由产品仓库管理。

## 原因与边界

原 `runtime_tool_invocations` 保存结果身份，但成功 Tool 引入的附件还保存在 `InvocationSucceeded.authorized_content` 中。Artifact 依赖、创作 checkpoint、消息附件和部分输出帧也含内容引用。仅检查 `presentation_content_refs` 或数据库外键，无法证明生成内容没有被历史记录引用。

新增索引属于原 Ledger 的派生数据，不引入另一套任务、结果提交或保留策略。它仅列出事件协议明确声明的 `ContentRef`。字符串、任意 JSON、嵌入字节和仅包含 ID 的其他业务结构不会被猜测为引用；这些结构的依赖仍须由各自领域持久保存和验证。该索引不能单独证明整个产品的引用图已经完整。

## 协议引用提取

`MW:apps/agent-runtime/crates/infrastructure/rpc-protocol/src/ledger_content.rs` 使用产品已有的 Protobuf 描述符和有界遍历器，处理 DomainEvent 与 OutputFrame。沿已知字段借用原始字节，只解码实际 `ContentRef`；按内容身份排序、去重，并拒绝同一 ID 的矛盾元数据。不增加新的实现依赖。

单记录继续受原 Ledger 4 MiB 上限约束，遍历深度限制为 32，字段工作量受输入字节预算限制。它不是事件语义校验器，也不授予内容访问权限。未知字段、重复或歧义编码、非法引用、越界输入不会产生“已完整分析且没有引用”的结论；遇到后部错误时不提交前部的部分引用集合。

## SQLite v187 与原提交事务

新迁移给原 `ledger_records` 增加 `content_reference_coverage`，身份、租户和来源摘要继续以原记录为准。状态为：0 尚未分析、1 已完整遍历已知类型字段、2 不透明或非法编码、3 未知记录 schema、4 历史正文已回收、5 超出当前分析边界。状态不是 Tool 或 Run 生命周期。

`ledger_content_references` 保存精确的内容身份、媒体类型、长度、摘要及原记录引用；索引支持按租户和内容身份查询。没有引用的正常记录不产生引用行。没有额外的逐日志身份副本表，异常分析状态使用原表的部分索引查找。

引用捕获在原 `append_in_transaction` 中完成，与 Tool、Artifact、草稿和幂等收据共用现有提交事务。SQL 失败使原事件和关联业务变更一起回滚。直接插入的日志默认停留在尚未分析状态，不会因漏调捕获而伪装为无引用。

数据库约束绑定原记录和租户，禁止完成后改写、替换或独立删除引用。正文压缩后仍保留已提取的引用身份，原记录经原有策略删除时级联删除派生行。这个目录不等于永久保留指令：后续回收还必须区分原 payload owner 已退役的输出帧与仍有效的领域事件，不能仅凭索引行存在让已退役帧永久占用内容。索引不对 Content Store 建立新的读取授权，也不恢复已显式擦除的内容。

v186 升级使用原迁移序列创建的历史数据库验证。迁移逐条检查正文大小并读取、核对摘要，不把整份日志载入内存；旧正文和摘要不被改写。未知或已回收正文保留明确分析状态，实际摘要损坏及迁移末尾失败回滚整个升级。升级仍是原数据库迁移事务，尚无大体量用户数据库的耗时结论。

最终协议库 97 项、SQLite 库 355 项测试通过，后者有 3 项跳过：两个子进程入口已由父测试调用，一个旧版外部数据库夹具未执行。创作回归 62 项通过、12 项跳过；其中三项真实导出提交已使用固定 worker 单独执行并通过，另外六项导出准备和三项旧外部环境测试没有在本阶段显式执行。修复专项 7 项与原日志回收 3 项通过，修复专项与完整库回归重叠，不累加为独立覆盖。

协议/SQLite 两个生产库的严格 Clippy、全工作区 all-targets 编译通过；工作区保留既有无关测试导入告警。全部七份接受的命令记录绑定同一份未变化的 Runtime 源码输入集合；早期实现、失败回归和单独诊断的原始记录保留，不算最终通过。没有运行完整产品测试套件。

实际两版交付各 12 份文件由既有独立读取器重新核对：首版与固定 SDK 基准逐字节一致，第二版实际 PPTX 的标题为修改后的值，五类质量声明仍只有结构为 passed。固定 SDK、worker 及输入不变；产品库测试读取的另 19 份自有夹具最终字节也与原封存来源一致。后者不在命令的 Runtime 源码清单内，不能宣称已对全工作区所有外部输入做命令前后快照。

扩大库回归发现两个历史升级夹具失败；单独重现的错误均为 `table content_material_writes already exists`。它们先创建当前数据库，再删除部分 v179–v182 表并改写版本号，因而仍含 v183 及后续结构，不能代表 v178/v180 旧库。已改用原历史迁移程序构造对应版本，再写入该版本允许的合成同意记录与暂停记录；不把重命名当前数据库视为历史升级验证，也没有放宽生产迁移。第三项失败来自启动进度测试仍期待复用 v133 的外键检查；后续迁移已改变关系，现明确要求对最终结构再次检查，生产启动逻辑不变。

修复后的上述三项测试及四项 v187 迁移测试通过。v187 夹具中的已回收正文已改为越过保留边界的 OutputFrame；不会将不可回收的 DomainEvent 人工清空作为正例。另三项原日志回收测试通过，包括新的真实内容文件 → 带引用的 OutputFrame → 原回收入口 → 数据库重开链路：正文合法退役，引用目录保持原身份和元数据，内容仍可读；已受其他领域保护的帧保持正文。该验证不代表已经开启内容文件的业务终态回收。

所改 18 个 Runtime 源文件均通过格式、空白和行数检查。命令、源码摘要、两版实际产物、原始失败及未执行范围见[阶段证据](../reviews/evidence/2026-09-27-product-ledger-content-roots-verification.json)。SDK 与 worker 继续采用上一产品阶段的固定材料，本次产品测试不为核心工作区同期其他改动提供新验收，也不构成性能或安装包测量。

整理证据时，共享读取器曾将成功测试名中的 `::error::` 误识别为错误文本；现按 Cargo/rustc 的诊断行及测试结果识别失败。五项读取器测试通过，包含该误判回归和真实失败、编号编译错误、缺失汇总、篡改日志及源码变化的拒绝检查。原始测试日志没有被重写，历史阶段证据保持原记录。

后续业务回收必须同时核对原 Tool 的真正终态、持久额度及所有领域引用，处理无法完整分析的记录。`Indeterminate` 不是真正终态。草稿、候选、Artifact 历史、模型与恢复记录中的非 Ledger 根仍需核对；这一阶段不删除任何生成内容，也不退役 Invocation 账户。
