# 原生持久任务调度

本阶段将已有标准宿主接入原生后台执行。任务、版本、资源和公开资产仍由同一个 SQLite owner 持有；没有另建任务库。[阶段证据](../reviews/evidence/2026-09-26-native-scheduler-verification.json)绑定本次源码和实际产物；不能据此宣称完整 MCP、浏览器宿主或 Musterwork 替换已完成。

## 调用与执行

`StandardHostConfig` 是可信 Rust 配置，包含数据库位置、执行器摘要、资源预算和可选 renderer 工厂，不接受从工具参数反序列化权限或路径。`NativeRuntime::start` 在启动前验证线程预算并建立全部工作连接，再统一放行线程；部分启动失败会停止并回收已创建的线程。

每个 `NativeSession` 有独立控制连接。`job` 请求在持久提交后返回任务；`sync` 和 `auto` 等待同一个执行池，不在控制线程另行运行文档计算。等待到期返回原有任务回执，后续查询相同任务。同步等待自己的操作使用原操作执行权限，独立 `getJob` 接口仍要求查询权限。输入继续使用纯操作层共享的有界严格解码器。

默认两个工作线程，可配置 1–16 个；轮询默认 250 ms，允许 10 ms–60 s；每批过期回收默认 32 个，上限 256。同步条件等待默认 1 s，上限 30 s，数据库调用仍有独立的 5 s busy timeout，不能将等待配置解释为整个调用的严格墙钟上限。这是每个 runtime 的执行并发上限，不是数据库所有进程的全局并发额度或整机内存上限。

控制会话释放不取消业务任务。runtime 关闭会停止新的调度迭代并等待已进入迭代的工作线程；每个这样的线程最多再领取和执行一个任务，其余任务保留在持久队列中。这里没有把线程 join 宣称为强制终止；长计算仍依赖检查点，原生绘图由现有隔离 worker 管理。

## 领取、租约与恢复

领取按注入的 scope、principal、操作权限以及任务锁定的 executor 过滤。选择与 `claim_record` 共用立即事务，执行 fence 和租约在同一提交中产生。已有显式 `claim/run_job` 与自动队列走同一领取和执行逻辑；不可变快照在领取事务提交后读取。

工作线程在轮询和执行前有界回收过期运行任务。回收可跨执行器版本，但不能越过 scope、principal 和操作权限。现有终态规则决定取消或中断结果，私有输出及配额通过原来的 `db::save` 事务路径回收。新执行器不会擅自改写其他执行器锁定的排队任务。

创建、编辑与导出现在共用 `ExecutionCheck`：计算检查点读取持久取消/租约，达到续期间隔时调用既有 `renew`。内部存储或租约错误保留原诊断，不被计算层的布尔取消信号掩盖。私有结果读取、写入使用相同 execution guard。最终提交继续验证权限、请求、版本、执行器和 fence，计算结束不直接代表成功发布。

工作线程 panic 或执行基础设施失败会停止该池接受新的操作，并通过能力目录返回 `executionUnavailable`；已有控制连接仍可查询和取消。失败后不能把已持久接受的任务伪装成未提交。正式协议层的请求取消、服务退出、业务取消映射仍需在 MCP 实现中落实。

## 数据库升级与查询成本

v4 → v5 只新增 `jobs_queued` 和 `jobs_expiring` 两个派生索引，不改写已有任务或资产行。按时间排序时显式转为整数，因为公共合同中的毫秒值以十进制字符串编码。索引创建和版本升级共用迁移事务，旧 receipt 非法 JSON 会导致升级失败并回滚，不通过丢弃记录完成升级。

队列直接查询 jobs，排队索引绑定 scope、principal、executor 和创建时间；过期索引绑定 scope、principal 和租约时间。测试对实际执行的 SQL 使用 `EXPLAIN QUERY PLAN`，检查范围索引及无临时排序。权限过滤仍可能检查索引范围中的其他操作记录，不能把返回一条记录解释为只读取一条记录；持久回执数量由宿主限额约束。

## 开发 CLI

`mo-host <database> <principal> <scope> --scheduled 2` 启动持久 NDJSON 控制会话和后台工作线程；可同时传入 `--preview-worker <path> <sha256>`。身份和配置是运行者参数，JSON 无权覆盖。该模式暂不与一次性的 `run/append/read-asset` 命令混用；二进制资源仍可通过同一数据库 owner 的独立 CLI 调用处理。

未加 `--scheduled` 的显式执行方式保留，能力目录如实区分 `explicitRun` 与 `hostScheduled`。CLI 不是正式 MCP 发行包；生产传输、并发请求/输出预算、SDK、Skill/Plugin、浏览器 owner 和 Musterwork Artifact 接入继续实施。

## 验证与限制

本阶段验证程序是 `tools/verification/native-scheduler-workspace.py` 与 `native-scheduler-reference.py`，所有新产物放在 `.codex-work/native-scheduler/`，不覆盖历史报告。验证包括多连接竞争、执行权限、会话释放、失败后控制、迁移回滚、真实进程终止重启，以及真实 renderer 忙碌时的查询、取消和同步请求排队。

837 项全仓 Rust 测试通过。随后完善了失败池的已有请求重试，以及准备阶段耗时后的首次续租时间；最终 61 项普通宿主测试及严格 Clippy 通过。2 项私有交付与 9 项导出集成使用真实固定摘要 worker，包含单 worker 忙碌期间的运行/排队取消、同步请求不越过并发预算，以及后续任务的完整公开资产核对。旧 v1 迁移夹具原来使用非法占位 JSON，现改为真正提交得到的 receipt，保持原字符串不变断言；非法 v4 JSON 另有升级回滚测试。

release CLI 执行了 40 次新增结构化调用，持久会话自动完成四次导出，涵盖启动前排队及 job/sync/auto 三种模式，重开后结果保持。另执行 31 次既有导出链路调用；两份真实 v3 库和一份真实 v4 库只对副本升级，原任务、资源和 12 个公开资产保持。109 份 Schema/TS 检查和十份实际 Native/WASM Schema 对照通过。72 次历史文件/编辑配对调用、两页实际绘制保持先前语义、字节及像素结果；自有合成字体语料不代表商业文稿视觉验收。

依赖树与上一阶段完全相同；新 Cargo.lock 仅增加内部测试依赖。相同锁定 release 配置下，Rust WASM 原始字节从 8,765,461 变为 8,764,177，gzip-9（mtime=0）从 2,423,678 变为 2,425,295。此数值只描述 Rust 模块，不包括 JS、绘制/塑形组件、字体/媒体及桌面包装，也不构成产品性能结论。

完整渲染对象、媒体、动画/转场、Office/WPS 编辑播放往返、全量性能与安装包体积仍须继续完成。当前线程数和持久字节配额不构成完整 CPU/RSS/进程终止预算。
